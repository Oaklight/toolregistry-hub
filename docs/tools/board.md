# Kanban Board Tool

The `board` namespace replaces the old stateless `todolist-update` tool. Every
project has its own entries, and every change is persisted to a local SQLite
file. The MCP daemon and the admin panel open the same file, so an agent can
create an entry in a session and a person sees it in the browser.

???+ note "Changelog"
    Unreleased: replaces `todolist-update`; adds projects, entries, statuses,
    priority, due date, labels, assignee, links and the admin Kanban tab.

## Why it replaces the todo tool

`todolist-update` took the whole list on every call and returned an
acknowledgement. It kept nothing, so two sessions overwrote each other, and a
model could not update one entry without resending all of them. The board tools
change one entry at a time and keep history.

## Model

- A **project** is a key (`KAN`), a name and a per-project sequence counter.
- An **entry** belongs to one project and has the id `<KEY>-<n>`, for example
  `KAN-12`. The sequence is never reused: deleting `KAN-7` leaves a permanent
  gap, so a stale reference can never point at a different entry.
- Statuses are the five kanban columns, in board order:
  `backlog`, `todo`, `in_progress`, `done`, `cancelled`.
- Entries are **soft deleted**: they keep their id and timestamps, and
  disappear from list and board views unless `include_deleted` is set.
- Projects are **archived** by default. `force` deletes the project and its
  entries. An archived project refuses new entries and updates; reads and
  entry deletion still work.
- A force-deleted key is retired, not forgotten: recreating a project with the
  same key continues its sequence (`SEQ-1..3`, force delete, recreate `SEQ`,
  next id is `SEQ-4`), so an old reference never resolves to a different
  entry.

### Status aliases

Input aliases are normalised before storage; stored values are always the
canonical ones.

| Alias | Stored |
| --- | --- |
| `planned` | `todo` |
| `pending`, `in-progress`, `inprogress`, `doing`, `active` | `in_progress` |
| `complete`, `completed`, `closed` | `done` |
| `canceled` | `cancelled` |

Priority accepts `urgent`, `high`, `medium`, `low`, and the aliases `p0`
(urgent), `p1` (high), `p2` (medium), `p3` (low).

### Timestamps

`created_at`, `updated_at`, `closed_at` and `deleted_at` are generated by the
server in UTC with microsecond precision. No tool accepts a timestamp
argument, so a caller cannot forge the audit history. `due` is a planning date
(`YYYY-MM-DD`) and is the only date a caller chooses.

`closed_at` records when the entry entered its current closed state. It
changes only on a transition: it is stamped when the entry moves into `done`
or `cancelled`, kept by edits and by re-saving the same status, and cleared
when the entry reopens.

## Tools

All tools are deferred; discover them with `discover_tools` and call them with
`call_deferred`.

| Tool | Purpose |
| --- | --- |
| `board-create_project` | Create a project (`name`, optional `key`) |
| `board-list_projects` | List projects with per-column counts |
| `board-archive_project` | Archive a project, or delete it with `force` |
| `board-create_entry` | Create an entry with all optional fields |
| `board-get_entry` | Read one entry by id |
| `board-update_entry` | Update title, content, priority, due, labels, assignee, links |
| `board-update_status` | Move an entry between columns |
| `board-delete_entry` | Soft-delete an entry |
| `board-list_entries` | List entries, filtered by project and status |
| `board-view` | Render a project as a markdown kanban |

`project` accepts a key or an exact name; `ref` accepts `KAN-12` in any case.

## Quick Examples

```python
from toolregistry_hub import BoardTools

board = BoardTools()  # shared default database
board.create_project("Kanban Board", key="KAN")
board.create_entry(
    "KAN",
    "Wire the board UI",
    content="Render five columns and the entry form.",
    status="planned",
    priority="p1",
    due="2026-12-01",
    labels=["ui"],
    assignee="pding",
    links=["https://github.com/Oaklight/toolregistry-hub/pull/1"],
)
board.update_status("KAN-1", "pending")
board.update_entry("KAN-1", content="First pass merged.")
print(board.view("KAN"))
```

## Storage

One SQLite file, WAL mode, permissions `0600`; the parent directory is created
`0700`. The path resolution order is:

1. an explicit path (`kwargs: {"db": ...}` in the tool config, or `--db` on
   the admin command),
2. `TOOLREGISTRY_HUB_BOARD_DB`,
3. `$XDG_STATE_HOME/toolregistry-hub/board.sqlite3`,
4. `~/.local/state/toolregistry-hub/board.sqlite3`.

The MCP daemon and the admin process must resolve the same file. Set the
environment variable in both systemd units so this cannot drift.

## Concurrent access

Each operation opens its own connection; WAL lets the tool and the admin panel
read and write at the same time, and `busy_timeout` makes a writer wait rather
than fail. Do not switch the database to `journal_mode=DELETE`.
